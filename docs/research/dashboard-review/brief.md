# Support-ticket dashboard

Complete the seeded support-ticket dashboard in this repository. It is a small, local product used by a support operator to find tickets, inspect their details, update their status and priority, and create tickets. Keep the twelve initial records in `tickets.js`, including their IDs and values. Work in the existing vanilla HTML, CSS, and JavaScript application; no dependencies, backend, remote requests, or external assets are needed. Store changes in browser local storage so they survive page reloads on the same origin.

The finished dashboard must provide:

- A ticket list showing each ticket's ID, title, customer, status, and priority, with a sensible visual hierarchy. All twelve seeded tickets appear initially. Supported statuses are `open`, `pending`, and `resolved`; priorities are `low`, `medium`, and `high`.
- Case-insensitive substring search across title and customer. Search, status filtering, and priority filtering combine using AND. Each filter can also select all values. Show the matching result count and a clear empty state when nothing matches. A `Reset filters` button clears search and both filters without changing stored tickets. Announce result-count changes with a live status region (`role="status"`).
- Ticket details opened from a button or link whose accessible name includes that ticket's ID and title. Show its title, customer, description, status, and priority. The operator can edit status and priority and use `Save changes`; saving updates the list and persists across reload. `Cancel` dismisses details without changing the ticket.
- A `New ticket` action opening a creation dialog. Title, customer, and description are required. Trim surrounding whitespace before validating or storing these fields; whitespace-only values are invalid. Invalid submission keeps the dialog open, shows meaningful accessible validation messages associated with the invalid fields, and creates no ticket. `Create ticket` saves a valid new ticket with a unique ID and the selected status and priority. The new ticket survives reload and can be found, inspected, and edited like seeded tickets. `Cancel` creates nothing.
- Usable controls and dialogs at desktop widths and a 360-pixel viewport, without horizontal page overflow or clipped dialog controls. Every action must be reachable and operable with the keyboard, with visible focus. While a modal is open, Tab and Shift+Tab cycle within its controls. Escape dismisses either dialog without saving, returning focus to the control that opened it. Use semantic buttons, inputs, selects, and dialogs with accessible names.

Keep these accessible names so operators and browser checks have a stable interface: `Search tickets`, `Status filter`, `Priority filter`, `New ticket`, `Reset filters`; dialog names `Ticket details` and `New ticket`; field labels `Title`, `Customer`, `Description`, `Status`, `Priority`; actions `Save changes`, `Create ticket`, and `Cancel`. No specific layout, colors, visual theme, or implementation structure is prescribed.

Start the local app with `python3 -m http.server 8000 --bind 127.0.0.1` and open `http://127.0.0.1:8000`. This is a static development server only; product data and persistence remain in the browser.

Run the public smoke check with `node test_existing.cjs`. The environment supplies `PLAYWRIGHT_MODULE`, pointing to an already installed Playwright module and browser. The smoke check starts a temporary local static server; it does not install anything. A missing runtime is a failed check, not a skipped success.
